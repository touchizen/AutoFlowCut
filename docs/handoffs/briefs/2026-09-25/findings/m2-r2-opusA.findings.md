[MAJOR] src/hooks/useVideoAutomation.js:602-615 (submit auth branch), :728 (poll loop guard), :940-947 (tail) and :750-765 (poll auth branch), together with electron/ipc/flow-angular.js:103,108,374 — F3 was fixed on the poll gate only. The T2V submit handler still passes its `sessionGate` result straight through, so `not-on-flow` or `wiz-missing` comes back as `authFailed:true`. That breaks the §3 rule "authFailed only for HTTP 401 / rpc code 16". In the hook, the submit auth branch then sets `authStopped`, which does two things: `while (… && !authStopped)` skips the poll loop entirely, and the tail marks every already-submitted pending item `{error, errorKind:'auth'}` while its `mediaId` is still null from the submit patch.
   - Failure scenario (reproduced with the real hook in a scratch run): p1 is submitted and pending, then p2 returns `{authFailed, errorKind:'flow-session-missing', error:'wiz-missing'}`. `checkVideoStatus` is called 0 times, and vscene_1 ends up `status:'error', generationId:'gen-1', mediaId:null, errorKind:'auth'`. After merging the way App does and calling `start()` again, `generateVideoT2V('p1')` runs again. That spends 10 more credits on a video that was already charged and exists in Flow.
   - The trigger is the same transient reload F3 was meant to handle. In Flow mode it is very exposed, because all fresh items are submitted in the first `fillWindow` with 7–15 s pacing (minutes of exposure).
   - The same patch, which loses the link to the charged video, is also written by a real 401/16 on the pre-click nzlxg read and by the poll-time `authFailed` branch.
   - Fix: in Flow mode, treat a pre-click submit auth refusal as "halt new submissions only". Mark this item and the remaining fresh items as auth and set `submitHaltRef`, not `authStopped`, so pending items keep polling. The poll gate is now per-item, and a real 401/16 still ends the batch. Also, in every Flow terminal patch for a pending item (auth, poll timeout, tail), keep `mediaId: submission.generationId`, since Flow's generationId is the mediaId. The next Start/Retry is then download-only instead of a re-submit. Add the 2-item test.

2. [MINOR] electron/ipc/flow-angular.js:514-524 (the author's F3 deviation) — On a real logout (the view sits on accounts.google.com), `not-on-flow` stays per-item `pending` forever.
   - Failure scenario (scratch run): the hook polls 120 × 10 s = 20 minutes, showing only "Polling N videos" and no login prompt. It then writes `{error:'Polling timeout — video generation took too long'}` with no errorKind and ends with `status:'done'` "⚠️ done — 1 failed". The cause shown is wrong, and the item can be re-submitted after re-login, so it gets charged twice.
   - Fix: keep F3's tolerance for transient failures, but count consecutive gate failures in the handler (reset on any passing gate). After N of them (e.g. 3, about 30 s), return top-level `{authFailed, errorKind:'flow-session-missing'}`. Alternatively, have the hook escalate when every pending status carries `pollError:'flow-session-missing'` for K consecutive polls.
