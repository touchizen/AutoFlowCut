1. [MAJOR] src/hooks/useProjectData.js:30 + :1228/:1373, src/services/videoRecovery.js:156, :175, :232-238, src/hooks/useVideoAutomation.js:348-349. This path already existed before c6d057e5 and is not on the one-item live-gate path unless the app restarts mid-run. It is the one remaining way a charged Flow video gets submitted again.
   - What is wrong: on load, `resetGeneratingItem` turns a submitted item (`generating` + generationId + mediaId:null) into `pending`. Only a recovery run that returns a status puts it back to `generating`. The hook only treats an item as in-flight when its status is `generating`.
   - Recovery is skipped entirely when `openFlowProject` is not confirmed, and nothing re-runs it later. It also leaves the item `pending` in three other cases: a non-success result (the comment at :175 says "'generating' 유지", but the item is `pending`), `authFailed` (break at :156), and an exception. Its `failed` branch drops `mediaId`/`errorKind`; this is the author's note (2), and main's per-id counters survive a renderer reload, so it can be hit.
   - Failure scenario: the user quits while a video is generating. On relaunch the Flow session isn't ready, so the project open is not confirmed and recovery never runs. The user signs in and presses Start. Checked with a scratch hook run using `resetGeneratingItem(persisted)`: `generateVideoT2V` was called once, the first poll was `["gen-new"]`, and the charged `gen-charged` was never polled. That is 10 more credits.
   - Suggested fix: persist an in-flight marker on the submit patch that is cleared by every terminal patch, and have Phase 0 classify on that marker instead of on `status`. Or: re-run `triggerVideoRecovery` when `flowProjectReady` turns true, and have the non-success/authFailed recovery branches set `generating`. Give the recovery `failed` branch the same shape as G3 (`errorKind`, `mediaId`).

2. [MINOR] src/hooks/downloadOnlyGate.js:6-19 with src/hooks/useVideoAutomation.js:541-542, :458-472.
   - What is wrong: G1(b) makes Flow items that were stopped, timed out or ended by poll-auth download-only, but they never passed `consumeGate.ensure()`, which only runs right before an in-batch download. `partitionDownloadOnly` still classes every download-only item without `download-entitlement` as "already charged on their original batch run", so Phase 0 re-downloads them with no batch consume.
   - Failure scenario (deterministic): Start 10 Flow videos and press Stop before the first one completes. Press Start again; the start gate passes while remaining > 0. Phase 0 downloads all 10 through `retryVideoDownload` and never calls `consumeBatchDownload`. Before G1(b) these items were resubmitted and their downloads were gated. Per-item Retry is already ungated by design, so the new leak is the batch path.
   - Suggested fix: persist a "download consumed" marker that is set only after the gate returns ok, and route download-only items without it through `consumeGate.ensure()` in Phase 0.

3. [MINOR] electron/ipc/flow-angular.js:509-543 (G2 counter) with src/services/videoRecovery.js:314-315, src/utils/errorDisplay.js:32, src/hooks/useVideoAutomation.js:479-499/:723.
   - What is wrong: `gateFailures` belongs to the handler instance. It counts calls, not poll rounds or time, is shared by every caller and carries over between batches. So "3rd consecutive ≈30s" only holds for the 10 s poll loop.
   - Verified with a scratch test: five concurrent `check()` calls during a single gate failure returned `[pollError, pollError, AUTH, pollError, pollError]`.
   - Failure scenario: Phase 0 runs 5 `retryVideoDownload` calls in parallel. With 3 or more download-only items, one transient reload at Start gives `authFailed` on the 3rd call. That item gets `{error:'flow-session-missing', errorKind:'auth'}`, and `resolveDisplayError` shows the raw token in the results table (a real 401 already showed `flow-rpc-error` here). Phase 0 then sets `authStopped`: fresh items are never submitted or patched, and the status stays `running` with "⚡ Re-downloading…" (the author's note (1)). Manual Retry clicks, and a count left over from a stopped batch, also add to the counter.
   - Suggested fix: fire only after at least 3 failures spanning at least ~25 s since the first failure (store a timestamp), or count per poll round. In `retryVideoDownload`, show the auth text when an authFailed result carries an `errorKind` (same rule as the hook's `authFailureText`). In the Phase-0 `authStopped` exits, call `setStatus('error')` with the auth message.
