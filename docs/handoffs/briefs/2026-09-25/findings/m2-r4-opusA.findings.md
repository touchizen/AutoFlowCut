# M2 review round 4 — reviewer A (Opus, general axis; Codex gpt-6-astra hit its usage limit mid-review) — e1c24fb3

1. [MAJOR] src/App.jsx:1440 — `handleVideoRetry`'s slow path now nulls `generationId`, `mediaId` and `downloadGated` on every call that misses the download-only fast path, not only on `forceRegenerate`. A plain "Retry" goes down this path for any error row that has `generationId` but no `mediaId`. `ResultsTable.jsx:423` and `FrameToVideoPanel` show "Retry" on those rows because `canDownloadOnly` is false. Those are the legacy auth/stopped/timeout shapes that provenance tests (c)/(c2) say must be polled and never resubmitted. Failure scenario (checked with probes): a Flow row is `error + generationId:G + mediaId:null` (errorKind auth). Pressing Start on it polls G and submits nothing. Clicking Retry instead writes `{status:'pending', generationId:null, mediaId:null}` (confirmed through the App.flowSessionReason harness) and toasts "click Start Generation". The next Start calls `generateVideoT2V` once: a second 10-credit charge, and the already-charged G is abandoned. This round's App test only pins the `forceRegenerate` call, so the H3 fix is undone by one visible click. Suggested fix: null the ids only when `opts.forceRegenerate` is set. For a plain Retry in Flow mode with `generationId && !videoPath`, either keep the ids so Phase 0 polls the item, or send it to `retryVideoDownload`, which needs only `generationId` (in Flow the generationId is the media id). Add an App test that a plain `onVideoRetry` on `error + generationId + mediaId:null` keeps `generationId`.

2. [MINOR] electron/ipc/flow-angular.js:538-545 — the H7 streak never expires. `gateFirstFailedAt` and `gateFailures` reset only when a check-video-status gate passes. So one old failure keeps the 25 s condition true indefinitely, for example a per-item Retry or a Stop during a view reload with no passing poll afterwards. Failure scenario (probe): one gate failure at t=0, nothing for 10 minutes, then a transient reload while Phase 0 runs its 5 parallel `retryVideoDownload` calls. The second concurrent call is the third failure in a row, and the span is 600 s, so it returns top-level `authFailed`. Phase 0 sets `authStopped` and the whole batch ends on the auth message without submitting its fresh items. Suggested fix: also record `lastFailedAt` and start a new streak when `now - lastFailedAt` is more than about 15–20 s (longer than one poll interval), or reset both counters at batch start. Add a test for the old-failure case.

3. [MINOR] src/hooks/useVideoAutomation.js:447 — `submittedFlow` classifies by provenance without checking which engine made the id. An API-mode (Veo) item whose `generationId` is an operation name now counts as in-flight in Flow mode. That covers `pending` after a restart and `error` after an API stop or timeout. Failure scenario: Flow polls the operation path through jwpduf and gets no record 4 times (or a pollError until the 120-poll budget runs out). It then closes the row as `flow-video-not-found` or `flow-video-fetch-failed` with `mediaId` set to the Veo operation name. The row then stays download-only in both modes; before this round it was generated fresh. `recoverInFlightVideos` already filters by engine (#R34-1). Suggested fix: add the same engine filter to `submittedFlow`, either a UUID-shape check or excluding ids that contain `/`. A UUID filter fails only the 4 provenance cases (fixture id `gen-charged`) in tests/hooks, so the fixture rework is one file.

4. [MINOR] electron/flow-rpc-protocol.js:171 — `/^[a-z0-9_]{1,64}$/` still accepts a single lowercase word of user text, such as "sunset" or "dragon_king". Failure scenario: after the hypothetical response-shape change, that text passes the check and is still printed at flow-angular.js:354 and :361, sent to `report(...)`, and shown to the user through `errorParams.actual`. Suggested fix: every video key in the HTrJv catalog sample starts with `abra_`, `veo_` or `omni_`. Require that prefix in the parser (`^(abra|veo|omni)_[a-z0-9_]+$`, at most 64 characters), or log and report the key only when it matches the model-family pattern and print a placeholder otherwise.
