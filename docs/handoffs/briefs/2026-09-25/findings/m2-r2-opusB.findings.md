1. [MAJOR] src/hooks/useVideoAutomation.js:947-961 (stopped), :901-904 and :963-967 (poll timeout), :751-766 and :941-946 (auth) — In Flow mode these terminal branches never write `mediaId`. A Flow `generationId` is the media id (electron/ipc/flow-angular.js:362 returns `generationId: gen.mediaId`), and the submit patch has already set `mediaId:null`. So the item ends as `error + generationId + mediaId:null`. That is not download-only, and App.jsx:1396 Retry needs `mediaId`. It is not in-flight either: recovery at videoRecovery.js:127 only takes `generating`/`pending`. F1 fixed this for `flow-video-fetch-failed` only. F3 now sends a real logout down this path: 120 × 10 s of `flow-session-missing` poll errors, then a generic "Polling timeout". — Scenario, verified with a scratch hook run: 120 gate poll errors → `{error:'Polling timeout — …'}` with no `mediaId`/`errorKind` → App-merged state → a second `start()` calls `generateVideoT2V` again and `retryVideoDownload` 0 times. The more common case is the user pressing Stop mid-batch. The 'stopped' text promises "Retry later or restart the app for auto-recovery", but Retry takes the slow path (reset to pending) and the next Start re-submits. That charges 10+ credits again for a video that already exists in Flow. — Fix: in Flow mode, add `mediaId: submission.generationId` (plus a kind) to the stopped, timeout and auth patches so the item becomes download-only, the same money-safe rule as F1. Alternatively keep them `generating` so they are classed as in-flight. Test stop and timeout followed by a second `start()`.

2. [MINOR] src/hooks/useVideoAutomation.js:57, 659-660 with electron/ipc/flow-angular.js:436 — For `flow-settings-not-applied`, the F8 signature (same kind + same params) is always the same. So `duration-not-offered:<d>`, `not-checked:duration`, `needs-trusted:*`, `settings-trigger-click-failed` and `resolution missing` all look identical, although duration differs per item (each scene's `targetDuration` snap). — Scenario, verified with a scratch run: items 1–2 are refused `flow-settings-not-applied` (e.g. a 10 s scene the panel lacks, or a delayed duration reset on a needed click). The order is the same on every re-run, so Start never reaches them until items 1–2 are deselected. — Fix: pass the driver `reason` (and/or the item's effective duration) as a non-param field and include it in the signature. Or make only batch-wide reasons terminal: model-/ratio-not-offered, input-mode-not-material, model-submenu-unknown, resolution missing.
