1. [MAJOR] src/hooks/useProjectData.js:248 (`isNewerSubmission`), also pinned the wrong way at tests/hooks/useProjectData.inFlightLoad.test.jsx:95. The I2 guard only covers the `mediaId == null` shape. Since G1(b), every Flow terminal patch for a submitted item also writes `mediaId = generationId`: stop, poll timeout (`flow-video-fetch-failed`), poll auth, `flow-video-not-found`, download-entitlement denial, and download/save failure. The loader still runs `remapVideoPath` on those rows. It attaches the older `t2v_N.mp4`/`i2v_N.mp4` found by `videoSaveId` and normalizes the row to `complete`. So the restart money-rule hole B1 reported is still open for the most common terminal shapes. The regression pin even requires that `pending + generationId + mediaId + videoPath:null` gets attached and marked complete. That shape is what a restart during a Phase 0 or per-row re-download leaves behind, and the file on disk there is usually the old one. — Scenario (verified with a scratch test: the real `loadProjectWithResources` output fed into the real hook in Flow mode): a scene has `t2v_1.mp4` → the user runs a full Start (complete items are re-submitted) → `G_new` is charged → Stop, or a 20-minute timeout → the row is `{error, stopped, generationId:G_new, mediaId:G_new, videoPath:null}` → the app restarts or the project is reopened → loaded as `{status:'complete', videoPath:'/proj/videos/t2v_1.mp4', generationId:G_new}`. Recovery skips it because it has a `videoPath`. Phase 0 treats it as fresh. The next Start calls `generateVideoT2V` once (a second 10-credit charge), and `G_new` is never polled or downloaded, while the old video is shown as its result. The same happens with I2V framePairs through `syncVideosIntoScenes`. — Fix: only attach a remapped file to a non-complete row that has a `generationId` and no persisted `videoPath` when the file's history sidecar `mediaId` equals `item.mediaId || item.generationId`. The simpler option is to drop the `mediaId == null` term, so any non-complete row with a `generationId` and no `videoPath` is left for recovery or Phase 0 (download-only or in-flight). Flip the fp_2 regression pin. Add a pin that runs the real loader and then the real hook on a stopped row with `mediaId` and an older file: 0 submissions, 1 `retryVideoDownload`.

2. [MINOR] src/App.jsx:1403 (`chargedFlowItem`) vs src/hooks/useVideoAutomation.js:450-451. I1's fast-path condition has no engine-shape filter, while I4 added one (UUID only) to the hook in the same round. A plain Retry in Flow mode on a row carrying an API operation name therefore still goes to `retryVideoDownload`. Such a row comes from an API-mode stop or failure, shaped `error + generationId:'models/veo…/operations/…' + mediaId:null`. Retry then polls the operation name through jwpduf. — Scenario: each click returns pending/pollError and shows "Video still pending on server — try again later". On the 4th click the no-record limit gives `{failed, flow-video-not-found, mediaId:<operation name>}`, and the row is download-only in both modes for good. That is exactly the outcome I4 was meant to remove. A related point: both predicates now tie money-rule protection to a UUID shape that `parseVideoSubmitResponse` never checks (it accepts any non-empty `[3][0][0]`). If Flow ever returns a non-UUID media id, a restarted in-flight item is classified fresh and re-submitted, and recovery (`isUuid`) skips it too. That is fail-open on money. — Fix: use one shared predicate in App, the hook and recovery. Prefer the negative filter ("no `/`", i.e. exclude operation names) so an unexpected id shape fails toward polling rather than re-submission. Add an App pin: Flow mode, plain Retry on an operation-name row takes the slow path with no `checkVideoStatus` call.

Add a fake option for the two-step re-render (group removed, then re-added after N ms), and a pin that fails on the first-differing-scan mutation.
