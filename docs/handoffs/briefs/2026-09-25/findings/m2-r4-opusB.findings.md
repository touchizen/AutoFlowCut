# M2 review round 4 — reviewer B (Opus, test & wiring axis) — e1c24fb3

1. [MAJOR] src/hooks/useProjectData.js:251/265 (T2V) and :300/310 (I2V). The loader can re-attach an old video file to an item that already has a newer, charged submission. This defeats the H3 provenance rule after a restart. It was already there before M2, but it is a money-rule hole on the restart path.
   - What is wrong: `remapVideoPath` finds the file by `videoSaveId`, ignoring the persisted `videoPath`. The loader then forces `status:'complete'`.
   - When it happens: the user regenerates a scene that already has `t2v_N.mp4` on disk (a full Start that includes complete items, or Regenerate followed by Start). The submit patch leaves the item as `generating` with the new charged generationId (`G_new`), `mediaId:null` and `videoPath:null`. If the app or page restarts before completion, the item loads as `complete` with the old file path, still carrying `G_new` and `mediaId:null`.
   - Effect: `triggerVideoRecovery` skips the item (`!vs.videoPath`). Phase 0 puts it in fresh because it is `complete` and has a `videoPath`. So `G_new` is never polled, the old video is shown as done, and the next Start submits the item again.
   - Verified: a scratch test fed the real `loadProjectWithResources` output into the real hook in flow mode. Loaded item: `{"status":"complete","generationId":G_new,"mediaId":null,"videoPath":"/proj/videos/t2v_1.mp4"}`. Result: `generateVideoT2V` called 1×, the charged id never polled.
   - Suggested fix: when the persisted item has `generationId`, a null `mediaId` and a null `videoPath` (a submission newer than any file), do not attach the remapped path and do not normalize to `complete`. Add a pin that runs the real loader and then the real hook and asserts the item is polled, not submitted.

2. [MINOR] electron/ipc/flow-angular.js:540-542. The H7 fix does not stop a count left over from an earlier batch from escalating, although its own comment says it does ("배치 사이 잔여 카운트"). Also, the count condition is not pinned by any test.
   - Stale timestamp: `gateFirstFailedAt` is never cleared by time. One leftover gate failure (for example the last poll before a Stop) makes the ≥25 s span true forever after.
   - Scenario, verified with a scratch test: one failed check, then 5 minutes later Phase 0 runs 5 concurrent `retryVideoDownload` calls during one transient reload. Results: `["pend","AUTH","pend","pend","pend"]`, so Phase 0 stops the batch with a false auth error. That is the B3 scenario again.
   - Count condition unpinned: removing `gateFailures >= GATE_MAX_FAILURES` (time only) still passes all 245 electron/services test files.
   - Suggested fix: restart the streak when the gap since the last failure is longer than about one poll interval (store `lastFailedAt`), or count at most one failure per short window so concurrent calls count once. Add pins for "leftover failure + 5 concurrent calls later → all pollError" and "2 failures 30 s apart → pollError".

3. [MINOR] src/App.jsx:1400/1440. H3 made the shared slow path clear `generationId`/`mediaId`, so a plain per-row Retry now makes a charged in-flight Flow item fresh. The brief says only Regenerate/Clear may do that.
   - Scenario: a row in the shape pinned by provenance tests (c)/(c2): `error` + `generationId` + `mediaId:null`. ResultsTable shows "Retry" on it (`canDownloadOnly` is false). Clicking it takes the slow path.
   - Verified with a scratch App test: the patch is `{status:'pending', generationId:null, mediaId:null, …}`, and the next Start then submits again instead of polling.
   - Reachability: in current code this shape only comes from legacy (pre-G1(b)) or cross-engine data.
   - Suggested fix: clear the ids only when `opts.forceRegenerate` is set. For a plain Retry on a Flow row with `generationId && !mediaId`, keep `generationId` (the next Start polls it), or clear it only when the id does not match the engine. Add an App pin for this case.

4. [MINOR] src/hooks/useVideoAutomation.js:936, :947, :1007 and src/App.jsx:1352/1886. Several H6 marker sites are not protected by any test.
   - Mutations that survived (all 357 files in tests/hooks, tests/components and tests/services green): removing `...gateMark()` from the stop tail (:1007), the `failed` branch (:936) and the per-item timeout (:947); separately, removing the i2v `downloadGated` pass-through in the batch whitelist (:1886) and in `handleVideoRetry` (:1352).
   - Effect if one of these is lost: Start N items, the first completes (batch consumed), Stop. The remaining items carry no marker, so the next Start calls `consumeBatchDownload` a second time for downloads from a batch that was already charged.
   - Suggested fix: add pins for "gate passed, then Stop, then Start → consume total 1" and "gate passed, then per-item timeout / failed → marker present", plus an i2v whitelist pin in App (true and null both pass through).

5. [MINOR] electron/flow-composer-settings.js:307-315. Live-gate risk from H4: after H4, the only check before the model click is the model itself. Every other option is validated after the click, and two things in that path are weak.
   - Model switch not recorded on failure: `steps.model = 'clicked'` is set only after the post-click re-plan succeeds. When it fails, the result and the `[Flow Settings]` log leave out the model switch. Verified: the model was clicked (`log3` contains `model:veo 3.1 - fast`), yet `steps` was `{"mode":"already(videocam)"}` with `reason:'duration-not-offered:8'`. Impact on the §12.2 no-credit probe: its pass condition is `steps.model === 'clicked'`. A Veo panel that was never observed rejecting 8 s, 720p or the ratio after a successful model click would make the probe neither pass nor show its named failure (`model-not-offered`).
   - Test harness does not match the live page: the fake Angular swaps the duration group synchronously inside the click handler. Production relies on a fixed `sleep(150)` before the rescan. If the live group re-renders later than that, the old model's options are planned again, which is the exact case H4 was meant to fix, and no test can show it.
   - Suggested fix: record `steps.model = 'clicked'` as soon as `applied` is true. Wait until the dependent groups are stable (two identical rescans, bounded) instead of a fixed 150 ms. Give the fake a delayed-swap option and pin both.
