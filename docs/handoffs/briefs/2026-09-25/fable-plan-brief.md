## What happened (read these first — they are the evidence)
1. `docs/handoffs/2026-09-24-flow-batchexecute-migration-HANDOFF.md` — why Flow mode broke. Google moved Flow from `labs.google/fx/tools/flow` to **`flow.google.com`**, an Angular app (`AiSandboxAngularFrontend`). The old Flow mode stood on three pillars that are all gone: (1) NextAuth session API → Bearer token, (2) direct aisandbox REST calls with that Bearer (status polling, media), (3) a page `window.fetch` monkey-patch that captured generation responses by URL (`batchGenerateImages`, `batchAsyncGenerateVideoText`, …). The new site sends **every RPC as an XMLHttpRequest POST to `/_/AiSandboxAngularFrontend/data/batchexecute?rpcids=<id>`** with cookie auth. The user-facing symptom: pressing generate/regenerate in the app says "Flow 로그인이 필요합니다" although the user is logged in.
2. `docs/handoffs/evidence/2026-09-24-flow-batchexecute-rpcids.md` — **the rpcid table from a live capture** (project open, two manual image generations, one manual T2V). ## Hard constraints (non-negotiable — from the user)
1. **No CDP for Flow automation.** No `webContents.debugger`, no `Network.*`/`Fetch.*`/`Page.addScriptToEvaluateOnNewDocument`. Allowed: `webContents.executeJavaScript` page scripts, the Flow preload bridge, `session.webRequest` for observation, `webContents.sendInputEvent` trusted clicks.
2. **Submits must come from a trusted click.** Both submit RPCs (`ogiZ0b`, `YhhmEf`) carry a reCAPTCHA Enterprise token that the page itself obtains (we never saw how). The app must never construct or send a submit RPC, never call grecaptcha. It types the prompt, sets settings, and clicks the real submit button with the existing trusted-click helper (`trustedClickOnFlowView` in `electron/ipc/shared.js`, `sendInputEvent`). A previous Chrome-extension attempt failed precisely on reCAPTCHA `isTrusted`.
3. **No video request-body tampering.** Injecting aspect ratio into video request bodies was tried before and the jobs died with `state FAILED` (commits `8821c558` → reverted `8305e773`). Video settings (mode, ratio, duration, resolution, count, model) must be set through the **settings panel DOM**. Do not add image body tampering in this work either; the DOM is the control surface.
4. Read-only RPCs (`jwpduf`, `as29s`, and if useful `Zzl0ze`, `nzlxg`) may be called by the app from the **page context** (same-origin XHR with `at`/`f.sid`/`bl` from `WIZ_global_data`, header `X-Same-Domain: 1`), **or** the app may capture the page's own polling. Decide with reasons (consider: the Flow view may be offscreen/hidden → Electron background throttling of page timers; Google changing payloads).
5. **Never log secrets or user content that Sentry could ship**: no `at`/cookies/tokens/signed URLs/emails/prompts in main-process `console.*` (Sentry's consoleIntegration turns main console lines into breadcrumbs). Existing code has the same rule — follow it.
6. **TDD for every change** (user rule): failing test first → minimal implementation → green. Protocol parsers/builders are pure functions with fixture tests built from the masked samples. UI-ish page scripts are tested the way the repo already does (jsdom / `vm` contexts — see `tests/electron/flow-new-project-button.test.js`, `tests/electron/flow-xhr-capture.test.js`, `tests/electron/flow-page-injection.test.js`).
7. **Surgical changes**: do not "improve" unrelated code; follow existing style (Korean comments are the house style). Remove only dead code your change creates.
8. Everything positional in batchexecute payloads can change when Google redeploys. The design must **fail loudly and specifically** (e.g. "ogiZ0b response shape changed at [0][0][6]") rather than silently produce wrong output, and the tests must pin the shapes.
